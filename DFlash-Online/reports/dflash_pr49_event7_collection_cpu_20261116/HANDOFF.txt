Purpose
-------
Determine how N7, E7 and S7 performed on the same 128 next-event requests, using the 384 generation records already saved in PR49. Each collector held a fixed event-seven checkpoint. Its parameters had not learned from that arm's event-eight feedback.

It does not identify a new algorithm or promise an upgrade. Its value is narrowing the explanation before spending more GPU time.

3. Reconstruct native counts, including terminal clipping
--------------------------------------------------------
Use the native convention already qualified in PR49, not a newly chosen metric.

For each verification block:
  draft = draft_tokens
  target = target_argmax
  w = verify_size
  c = committed_progress
  a = first mismatch index between draft and target, or len(draft) if all match

Check integer types for widths, progress and count fields, then:
  w == len(draft) + 1 == len(target), 1 <= w <= 16
  1 <= c <= w, c <= a + 1
  committed_tokens == (draft[:a] + [target[a]])[:c] == target[:c]
  output_start == cumulative prior committed_progress
  anchor_token == response_ids[output_start]
  committed_tokens == response_ids[output_start+1 : output_start+c+1]
  positions == range(prompt_length+output_start, prompt_length+output_start+w)
  raw_accepted_draft_tokens_before_stop == a
  accepted_draft_tokens == min(a, c)
  native_accepted_draft_tokens == c - 1
  stop_clipped == (c < a + 1)

Reconcile any retained finished flags with the pinned hook's termination convention.

For request i and arm X:
  V_Xi = number of verification blocks
  P_Xi = sum of committed_progress
  A_Xi = sum of native_accepted_draft_tokens
  M_Xi = sum of accepted_draft_tokens

Require:
  P_Xi = len(response_ids) - 1
  A_Xi = P_Xi - V_Xi
  metadata totals actually stored agree with the reconstructed totals

Native A is reconstructed from trace[*].native_accepted_draft_tokens; it need not exist as a top-level metadata field.

A is the PRIMARY native accepted-proposal count. M is a separate matching-count audit column. Never substitute M for A: stopping can make them differ. The initial prefill token is not a verified draft proposal.

With identical output arrays, P_Xi is common across arms. Thus acceptance and call savings are algebraically linked; they are not two independent proofs of a mechanism. A legitimate V=0 request stays in all 128 rows, contributes zero A and zero V to pooled totals, and has an undefined per-request acceptance ratio; do not impute a ratio or drop the request.

Do not align verification blocks, rejection slots or walks across arms. Different drafts change block boundaries. These records alone do not identify repair retention, gradient conflicts or the causal role of individual loss rows.

4. Fixed quantitative reduction
-------------------------------
Report ALL three contrasts in a declared order:
  E versus N; S versus N; E versus S.
Positive values below favor the first named arm X over reference Y.

Per arm:
  request count, output tokens, EOS/cap/zero-call counts;
  total V, A, P and audit-only M;
  pooled native acceptance L_X = sum_i A_Xi / sum_i V_Xi;
  committed progress per call = sum_i P_Xi / sum_i V_Xi.

Per contrast:
  absolute acceptance change = L_X - L_Y [tokens per verification];
  relative acceptance change = 100 * (L_X / L_Y - 1) [%];
  call reduction = 100 * (sum V_Y - sum V_X) / sum V_Y [%];
  net calls saved = sum_i (V_Yi - V_Xi) [calls];
  gross saved = sum_i max(V_Yi - V_Xi, 0) [calls];
  gross added = sum_i max(V_Xi - V_Yi, 0) [calls];
  number of requests with fewer/more/tied calls for X;
  audit identity: net saved = gross saved - gross added.

Include a 128-row paired table with every request's counts and all three call differences, so concentration in a few requests is visible without a favorable subgroup analysis. Do not substitute the mean of per-request ratios for pooled acceptance.

Uncertainty:
- Sort by the authenticated sealed source ID, with request ID as a declared tie-breaker.
- NumPy Generator(PCG64(1708)); 10,000 draws of 128 request indices with replacement.
- Use the SAME draws across all arms and contrasts; a request's entire three-arm record travels together.
- Recompute pooled quantities from sampled total counts for each draw.
- Report linear 2.5th/97.5th percentile intervals for absolute/relative acceptance change and call reduction. Store the ordered source-list hash, draw-matrix hash, NumPy version and percentile method.
- Handle any undefined denominator explicitly, including undefined draws; do not silently drop/redraw them or turn them into zero. Explain which interval cannot be defined if this occurs.

These are descriptive paired-request intervals conditional on one origin/seed and the reused collection population. They are not training-seed replication, multiplicity-adjusted confirmation or a correction for the project's prior method selection. Publish the three point estimates and intervals together. Do not invent an efficacy threshold, tune a method, or declare an algorithm selected from their signs.

EXCLUDE all collection elapsed-time, generation-time and request-latency rankings. Features were captured and other GPU tasks overlapped. Call reduction is a decoding-work proxy, not a measured speedup percentage. No block-level bootstrap, independent-arm bootstrap or 384-independent-sample claim.
